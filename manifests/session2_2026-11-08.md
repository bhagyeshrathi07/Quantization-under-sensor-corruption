## 6. Judge trial, development files (stability repeat 1, 35 VQA answers per precision)

**Candidate A, DeepSeek V4 through the team's LiteLLM proxy (`https://aiapi.paid.lol/v1`).** First attempt: the key exposed `deepseek-v4-flash` and `deepseek-v4-pro` (not the `-ron` aliases) and every call returned 402 `Insufficient Balance` from DeepSeek upstream; errored records were discarded. Second attempt later the same day with a reissued key that exposes `deepseek-v4-flash-ron` and `deepseek-v4-pro-ron`, run from the local machine against the synced development files (no GPU needed, the key never touched the host). Findings:

1. V4 behind the proxy is a reasoning model. With the released settings the probe spent all 512 completion tokens on reasoning and returned no score; with `max_tokens` 2048 the same (2048 reasoning tokens); `reasoning_effort: low` changed nothing; `reasoning_effort: none` turned thinking off (0 reasoning tokens, 445 completion tokens, score 36). Trial settings: `max_tokens` 2048, `reasoning_effort: none`.
2. Flash: 40 of 40 scored, zero errors, scores 4–36; BF16 cell means perception 26.3, planning 13.0, prediction 21.8; INT4 26.4 / 9.1 / 17.3; extraction rule `released` on 38 of 40, `markdown` on 2; mean usage 897 prompt / 317 completion tokens, 3.4 s per call at 4 workers. Projected cost from these tokens at the proxy's table rates (not a measured charge): matrix $2.97 unweighted, $2.66 weighted by the matrix cell mix (the trial is 14 / 14 / 12 answers per cell, a matrix run 133 / 399 / 40); with mitigation and validation $4.76.
3. Pro (trialled as well, marginal cost under $0.10): 40 of 40, zero errors, scores 3–46; BF16 means 32.3 / 19.3 / 20.7; INT4 31.0 / 11.4 / 13.2; `released` 38, `markdown` 2; 897 / 252 tokens, 4.7 s per call. Projected matrix $9.99 unweighted, $8.82 cell-weighted; programme $16.00.

Agreement on the 20 shared answers per precision: flash vs pro mean absolute difference 6.55 (BF16) / 5.05 (INT4), flash lower by 3.95 / 1.15 on average, Pearson 0.73–0.79. The local judge (below) vs flash: mean absolute difference 9.45 / 9.0, local lower by 8.15 / 4.9 on average but higher on 3 / 7 of 20 answers; vs pro 12.7 / 8.85, local lower by 12.1 / 6.05, higher on 2 / 4 of 20. Agreement between judges is not validity. The DeepSeek records sit in the same sidecars as the local-judge records, under their own settings hash.

Identity caveat: the records of this trial carry the alias (`deepseek-v4-flash-ron`), the endpoint and the settings, and nothing about what answered behind the proxy; the cost note's earlier claim that records name the upstream id was wrong. DeepSeek's model page (read November 8) says the legacy name `deepseek-v4-flash` routes to DeepSeek-V4.1-Flash-1017 and `deepseek-v4-pro` is DeepSeek-V4-Pro-0813, which is official routing, not proof of this proxy's backend. `reasoning_effort: none` is verified through this proxy only; DeepSeek's own API documents `thinking: {type: disabled}`.

**Candidate B, local open weights (`scripts/serve_judge.sh`, `openai/gpt-oss-20b`, revision unpinned in this trial, port 8001, `manifests/serve_judge.txt`).** Compat check accepted `max_tokens` and `reasoning_effort`. Two findings:

1. With the released settings (`max_tokens` 512) every reply was cut off: the model is a reasoning model and spent ~400 reasoning tokens before the rubric. With `max_tokens` 2048 and `reasoning_effort: low` (a temporary config, `/workspace/judge_trial_local.yaml`), 40 of 40 answers were scored.
2. The released extraction regex (`Total Score:\s*(\d+)`) matched only 14 of 40 replies: the model writes `**Total Score:** 15/100`, table cells, or a sum `0 + 5 + 8 = **13**`. `qflip.judge.extract_score_rule` now adds markdown-tolerant fallbacks and records the rule per record (`released` 14, `markdown` 23, `arithmetic` 3 in this trial); every variant seen is in the tests.

Measured usage (mean per call): prompt 953 / 955 tokens, completion 421 / 363 (reasoning 62 / 46 of those), latency 3.5 / 3.0 s at 4 concurrent requests. Scores are low across the board: BF16 means perception/VQA 20.9, planning 8.4, prediction 6.3; INT4 20.1 / 6.0 / 12.0; range 0–31 (20 answers per precision). Whether this judge is usable depends on the 100-answer human agreement check and the noise test, not on this trial. A full matrix with it would take about 4,576 × 3.3 s / 4 ≈ 1 hour of GPU (under $1). The trial served gpt-oss-20b without a pinned revision (`manifests/serve_judge.txt`, `revision:` empty); a frozen local judge needs `JUDGE_REVISION`, and `serve_judge.sh` now refuses an empty one outside `JUDGE_ALLOW_UNPINNED=1` trials.

### Fixes after the reviewer's passes (November 8 and 11, 93 tests)

1. Score extraction (`qflip.judge.extract_score_rule`, now version 4): the released regex returned the first term of an unbolded sum (`Total Score: 0 + 5 + 8 = 13` read as 0) while the bolded form read 13, and an incomplete sum returned its first term. Version 3 parsed the line as a whole; the November 11 pass showed it still accepted `13 =`, `0 + 5 + 8 = 13 +`, an unbalanced parenthesis, and read `99.5` as 99. Version 4 accepts only a complete expression (`0 + 5 + 8 = 13`, `13 (0 + 5 + 8)`, `13 = 0 + 5 + 8`, digit-free prose around it), both sides equal, delimiters balanced, no trailing operator, and rejects a decimal rather than truncating it; `released` is reported only when the upstream regex gives the same value. All 120 stored trial records read identically under version 4 (checked by a test); `08 --reparse` re-reads a sidecar's stored replies in place without any call, and a record rejected at write time stays rejected.
2. The judge freeze binds the extractor (version, and a digest of its source and of every regex's pattern and flags, since `IGNORECASE` alone changes what parses) like a template; every record names the extractor version it was scored with; production scoring (`05 --vqa`) re-reads each selected reply under the live, freeze-checked extractor and never trusts the stored number (a changed value is kept as `score_recorded`; an unparseable, empty or missing reply is stale, whatever number the record carried).
3. Backend identity: every record carries the provider's response model id, response id, system fingerprint and request time, plus the non-secret `judge.backend` description from config (provider, upstream model id from the proxy's routing table, local checkpoint revision, thinking control). One predicate (`qflip.judge.record_backend_status`) decides whether a record was written under an expected backend, and it is shared by resume in `08` (a scored record under another description or response model is judged again, not skipped), by `freeze_judge.py --records` (only records written under the description being frozen are evidence, and they must carry one response model id, which is frozen with the description; records from before the description existed count only for an empty description, no identity is invented) and by production scoring in `05` (development files: the live description; final files: the frozen description and response model). A final-split reply from another backend is kept, never scored, and marked `rejected` so no reparse restores it. A local judge (`localhost` or any loopback address, IPv6 included) needs its revision in config; the freeze checks the serve manifest, and final-split judging checks the running server the way the study servers are checked: served alias and model card `root` at the endpoint, the manifest pid alive with the model, port and `--revision` on its command line and owning the listener. `serve_judge.sh` refuses an unpinned checkpoint unless told it is a trial.
4. Third pass (November 11): resume and freeze evidence still trusted the stored score field, so a record whose reply the current extractor rejects (`Total Score: 13 =`) was skipped on resume and accepted as evidence; and after a limited re-judging under a new backend the summary still counted the old backend's records as scored. One function, `qflip.judge.usable_score` (expected backend, then the stored reply re-read under the current extractor; the stored number is never the criterion), now decides in all four places: resume, freeze evidence, the `08` summary (which reports scored, stale with reasons, and pending separately) and production scoring.
